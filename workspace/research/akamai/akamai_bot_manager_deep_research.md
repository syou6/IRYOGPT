# Akamai Bot Manager v2/v3 — Deep Technical Research Report

**Research Date**: 2026-03-30
**Scope**: Detection mechanisms, sensor telemetry, bypass techniques, ML models, challenge types

---

## Executive Summary

Akamai Bot Manager operates as a multi-layer, adaptive anti-bot system combining TLS/HTTP fingerprinting, JavaScript-based sensor telemetry collection, behavioral biometrics, device fingerprinting, and machine learning risk scoring. The `_abck` cookie is the central token encoding session trust. Sensor data (v2: ~58-field array, v3: cookie-hash-encrypted variant) is submitted to a collector endpoint, and Akamai assigns a 0–100 risk score. As of 2025–2026, TLS fingerprinting (JA3/JA4) and HTTP/2 fingerprinting are the most robust detection vectors; the JavaScript sensor layer is reverse-engineerable but regularly re-obfuscated. No single bypass technique is fully reliable at scale.

## 1. Cookie Architecture

### Three Core Cookies

| Cookie | Purpose | Lifetime |
|--------|---------|---------|
| `_abck` | Primary bot detection token. Summarizes session trust: contains timestamps, behavioral references, challenge outcomes, signed token. Validated on every request. | ~1 year once trusted |
| `bm_sz` | Session state for behavioral anomaly detection (Bot Manager Premier). Seeds the sensor encryption key in v3. Refreshed ~every 4 hours. | ~4 hours |
| `ak_bmsc` | Performance/telemetry optimization. HTTP-only; not accessible to JS. | Session |

### _abck Cookie Generation Flow

1. Browser loads a protected page, receives an unsigned `_abck` with a temporary bm_sz value (default seed `8888888` on first visit).
2. Akamai's injected sensor JavaScript executes and collects telemetry.
3. Browser POSTs `sensor_data` to the collector endpoint (typically `POST /akam/11/<path>` or similar obfuscated path).
4. Akamai server validates the payload, computes risk score, and issues a signed `_abck` cookie.
5. Subsequent requests must include the valid `_abck` cookie. Inconsistencies or stale timestamps trigger re-challenge.

**Invalidation triggers**:
- Stored behavioral data looks inconsistent or outdated
- Server-side detection of pattern anomalies (too-regular timing, missing events)
- Cookie value tampering

## 2. Sensor JavaScript — The 527 KB Collector

### Script Characteristics

- Heavily obfuscated using custom control-flow flattening, string encoding, and dead-code injection
- Dynamically loaded; the script hash changes per deployment, which is used as an encryption seed in v3
- Typical size observed in the wild: ~400–600 KB (commonly cited as ~527 KB)
- Deobfuscation tools exist (AST-based: `rastvl/akamai-deobfuscator-2.0`, `voidstar0/akamai-deobfuscator`)

### Sensor Data Payload Format

**v2 format**: A 58-element array, concatenated as a colon-delimited string, then encrypted:
- Step 1: Elements shuffled using PRNG seeded with the **JavaScript file hash**
- Step 2: Each character substituted using PRNG seeded with the **bm_sz cookie hash**
- Result submitted as the `sensor_data` form field

**v3 format**: Header field `x-acf-sensor-data` or similar, structured as:
```
3;0;1;0;<cookie_hash>;placeholder;placeholder;<encrypted_payload>
```
- Encryption keys: file hash (for element swap) + cookie hash (for char substitution)
- PRNG formula: `seed = ((seed * 65793) & 4294967295 + 4282663) & 8388607`
- `akamai-bm-telemetry` header: base64 encoding of the `sensor_data` content

## 3. Sensor Data Fields — What Is Collected

Based on reverse-engineering of multiple versions (1.69 through 2.x), the 58-field array contains the following categories. Field positions use negative integer IDs in the decoded format (e.g., `-100`, `-101`).

### 3a. Device / Browser Fingerprint Fields

| Field Range | Data Captured |
|------------|--------------|
| User agent string | Full UA, parsed for browser type/version |
| `-100` area | UA capabilities |
| `-101` area | Language/locale codes |
| Screen dimensions | `screenWidth`, `screenHeight`, available dimensions, color depth, pixel depth |
| Timezone offset | Numeric offset |
| Plugin enumeration | `pluginInfo`, plugin count (`plen`) |
| Storage capabilities | sessionStorage, localStorage, IndexedDB availability |
| WebRTC info | ICE candidate leak data, local IP if detectable |
| Battery status | If Battery API available |
| Automation detection | `navigator.webdriver`, Phantom/webdriver flags, DOM automation markers |
| `bmak.gd()` | Custom Akamai detection function output |
| `bmak.fpcf.fpValstr` (field ~70) | Fingerprint value string |
| Field ~129 (`w`) | Previously unparsed variable, added in later toolkit versions |

### 3b. Canvas Fingerprinting

- **`canvasFp1` and `canvasFp2`**: Two separate canvas render hashes
- Considered the **most critical and least forgeable field** in the sensor payload
- Generated by rendering a specific text string + shapes to an offscreen canvas and hashing the pixel output
- Akamai collects real fingerprints from browsers; the hash must match the device's actual GPU/rendering pipeline
- Noise injection detection: if canvas output is blank, identical across sessions (static spoof), or shows anomalous patterns, Akamai flags it
- Requires collecting live canvas fingerprints from real browsers to spoof effectively

### 3c. WebGL Fingerprinting

- **WebGL renderer string** (GPU model, e.g., "ANGLE (Intel, Intel(R) UHD Graphics...)")
- **WebGL vendor string**
- **WebGL extensions hash**: hash of the supported extension list
- **GPU hash**: derived from renderer + vendor
- Mismatch between claimed UA (e.g., Chrome on Windows) and WebGL renderer (e.g., Linux Mesa) is a high-signal detection event

### 3d. AudioContext Fingerprinting

- Renders a short audio buffer through an OscillatorNode + AnalyserNode pipeline and hashes the output
- Output varies by OS audio stack and hardware
- Safari 17+ Private mode injects small noise into AudioContext output — Akamai's system accounts for this variance range
- Completely static or completely randomized audio hashes trigger suspicion

### 3e. Font Enumeration

- `runFonts`: tests presence of fonts by measuring rendered text width differences
- Hashed list of detected fonts
- Inconsistency between claimed OS and detected font set is flagged (e.g., claiming macOS but having a Windows-only font set)

### 3f. Behavioral Biometrics — Event Telemetry

Akamai collects continuous event streams. Each stream has velocity (`_vel`) and count (`_cnt`) fields:

| Field | Captures |
|-------|---------|
| `me_vel`, `me_cnt` | Mouse movement velocity and count |
| `ke_vel`, `ke_cnt` | Keyboard event velocity and count |
| `te_vel`, `te_cnt` | Touch event velocity and count |
| `pe_vel`, `pe_cnt` | Pointer event velocity and count |
| `doe_vel` | Device orientation event velocity |
| `dme_vel` | Device motion (accelerometer) event velocity |
| `vc_cnt` | Visibility change count (tab switching) |
| Mouse coordinates (`-102`, `-105`) | Pointer coordinate sequences with timestamps |
| Motion trajectory (`-110`) | Full movement sequences with timestamps |

**What Akamai's ML looks at in these streams**:
- **Mouse movement entropy**: Human mouse paths have natural curvature, acceleration/deceleration profiles, and micro-tremor; bot paths are too straight, too smooth, or perfectly algorithmic
- **Keystroke dynamics**: Humans show variable inter-key timing (dwell time, flight time); bots have mechanical uniformity (e.g., exactly 50ms between every keystroke)
- **Scroll patterns**: Humans scroll in variable bursts with deceleration; bots often scroll in exact pixel increments or at constant velocity
- **Time-to-first-interaction**: Suspiciously fast first interaction (< 100ms) after page load indicates pre-scripted automation
- **Event absence**: Zero mouse movement events on a page where a form was filled is a strong bot signal

### 3g. Timing and Session Metadata

- Page load timestamps
- Time elapsed since cookie creation
- Challenge outcome timestamps
- Cookie state marker (`n_ck`: indicates new cookie)
- Authorization/target URLs (`-112`)
- Cookie/session identifiers with timestamps (`-115`)

## 4. Device Fingerprinting Beyond Navigator Properties

### 4a. TCP-Level OS Fingerprinting (p0f)

Akamai uses **p0f-style passive TCP fingerprinting** to detect the underlying operating system from TCP packet structure (TTL, window size, TCP options order). This is compared against what the browser's User-Agent or Client Hints claim:
- Chrome on Windows has a known TCP signature; Chrome on Linux does not match
- This creates an **OS consistency check** that is difficult to spoof at the application layer

### 4b. TLS Fingerprinting — JA3 and JA4

**JA3** (MD5 of concatenated):
1. TLS version
2. Cipher suite IDs (comma-separated)
3. Extension type IDs (comma-separated)
4. Elliptic curve IDs
5. Curve format IDs

Each browser version has a consistent JA3 hash. Python's `requests` library, curl, and automation tools produce distinctly non-browser JA3 values. Akamai maintains a blocklist of known-bot JA3 hashes.

**JA4** (Akamai introduced commercially, ~2024–2025):
- Sorts cipher suites and extensions alphabetically before hashing
- Resistant to order-randomization bypasses that defeated JA3 spoofing
- Format: version + cipher_count + extension_count + first_ALPN + sorted_ciphers_hash + sorted_extensions_hash
- Catches many automation libraries that had learned to randomize JA3

### 4c. HTTP/2 Fingerprinting (Akamai H2FP)

Akamai pioneered HTTP/2 passive fingerprinting (published at Black Hat EU 2017). The fingerprint captures:

| Component | Details |
|-----------|---------|
| SETTINGS frame | `HEADER_TABLE_SIZE`, `ENABLE_PUSH`, `MAX_CONCURRENT_STREAMS`, `INITIAL_WINDOW_SIZE`, `MAX_FRAME_SIZE`, `MAX_HEADER_LIST_SIZE` |
| WINDOW_UPDATE | Connection-level window size increment value |
| PRIORITY frames | Stream dependency, weight, exclusivity |
| Pseudo-header order | `:method`, `:authority`, `:scheme`, `:path` ordering |

Fingerprint format: `S[;-separated values]|WU value|P[,-separated priority data]|PS[pseudo-header order]`

Chrome, Firefox, Safari, and Edge each produce distinct H2 fingerprints. `requests`, `httpx`, `aiohttp`, and curl produce easily identifiable non-browser signatures.

## 5. Canvas Fingerprint Noise Injection Detection

Akamai's sensor specifically checks for canvas anti-fingerprinting techniques:

**What Akamai detects**:
1. **Blank canvas**: Some privacy tools return an all-zero pixel buffer — immediately flagged
2. **Static hash across sessions**: A never-changing canvas hash that matches no known GPU signature triggers suspicion
3. **Per-pixel noise injection**: Adding ±1 per-pixel noise (e.g., via Canvas Blocker extension) produces a hash that changes every render. Akamai detects this by rendering the same canvas multiple times within one session — if the hash differs each time, noise injection is confirmed
4. **Extreme deviation from expected GPU output**: The rendered output is compared against a model of expected GPU rendering behavior; radical deviations indicate software rendering or spoofing
5. **Canvas2D vs WebGL inconsistency**: If canvas rendering claims Chrome on Windows but WebGL reports a Linux GPU driver, the fingerprints are inconsistent

**Why random noise fails**: Akamai collects multiple canvas samples per session. Statistical consistency across renders is checked. Consistent noise (same random seed per session) is detectable via session correlation; inconsistent noise is detectable within a session.

## 6. Timing-Based Detection

### Page Load Timing
- **First-byte timing**: How quickly the first request follows page delivery
- **Sensor submission timing**: Humans take 2–30 seconds to interact; bots often submit sensor data within milliseconds of page load
- **JS execution timing**: The sensor script measures how long various computations take (WebGL render, canvas render, font measurement) — unusual timing indicates headless browser or emulated environment

### Interaction Timing
- **Inter-event intervals**: Mechanical precision (e.g., exactly 100ms between mouse events) is a bot signal
- **Mouse velocity profiles**: Too-smooth deceleration curves, perfect Bezier paths, or random noise trajectories all differ from human patterns
- **Scroll consistency**: Humans vary scroll speed and direction; bots scroll in constant increments

### Cookie Coherence Timing
- The `_abck` cookie contains timestamps. Requests with cookies that are too old, too new, or show impossible time jumps (e.g., future timestamps) are flagged.
- Field `-115`: session identifiers carry timestamps that must be internally consistent

## 7. Machine Learning Models

### Feature Set (Inferred from Research)

Akamai's ML models (confirmed: used in Bot Manager Premier) operate on two levels:

**Per-request features**:
- IP reputation category (residential/mobile/datacenter/VPN/TOR/proxy)
- TLS fingerprint hash match against known-bot database
- HTTP/2 fingerprint match
- Header ordering and completeness (missing headers, wrong order)
- Request anomaly score (out-of-order headers, version mismatches, malformed requests)
- User-Agent vs. Client Hints consistency
- Geographic/ASN anomalies

**Per-session behavioral features**:
- Mouse movement entropy (Shannon entropy of coordinate deltas)
- Velocity profile consistency (standard deviation of inter-event intervals)
- Event count ratios (mouse:keyboard:scroll ratios typical of human navigation)
- Time-to-first-interaction
- Canvas fingerprint stability across renders
- AudioContext fingerprint consistency
- Font detection results vs. claimed browser/OS
- WebGL renderer vs. claimed OS
- TCP OS fingerprint vs. UA OS
- Session length and page progression patterns

### Scoring System

- **0 = human**, **100 = bot** (confirmed by official docs)
- Three response tiers:
  - Cautious (low score, ~1–30): Monitor only, allow through
  - Strict (medium score, ~30–70): Issue challenge, secondary evaluation
  - Aggressive (high score, ~70–100): Deny, tarpit, or serve fake content
- Scores are **continuous and cumulative** across the session — a session that starts with legitimate behavior but then exhibits bot patterns will be re-scored
- **No publicly confirmed exact threshold numbers** for challenge triggers

## 8. Challenge Types

### Invisible/Crypto Challenge (Primary)
- Triggered when bot score reaches the "Strict" tier
- Browser receives JavaScript that executes a **proof-of-work cryptographic puzzle**
- The puzzle requires iterative hash computation (CPU-bound) designed to be trivial for humans (background tab) but expensive for bots at scale
- Result POSTed to `/_sec/verify?provider=crypto`
- A `sec_cpt` cookie is used during this flow
- Verification response at `/_sec/cp_challenge/verify` returns JSON with `success: true/false`
- Bot passing this challenge still needs to satisfy sensor data requirements

### Pixel Challenge (Advanced / Premier)
- Not widely documented; appears to be an invisible pixel-level test embedded in page rendering
- Likely validates that a real browser rendering engine produced the correct pixel output for a test canvas/image element
- Distinguishes between real GPU rendering and software-rendered headless browsers

### Interactive Challenge (Google reCAPTCHA or Akamai Native)
- Reserved for highest-risk sessions
- Two documented types: Google reCAPTCHA and "Akamai crypto challenge" (interactive mode)
- Triggered when invisible challenge fails or when risk score is extremely high

### HTTP Status Codes

| Code | Meaning |
|------|---------|
| 403 | Invalid/mismatched cookie, blocked request |
| 428 | Same request pattern repeated — crypto challenge required |
| Timeout | Missing or incorrect cookie, connection held |

## 9. Rate-Based vs. Behavior-Based Blocking

### Rate-Based (Applies Regardless of Bot Score)
- Requests-per-second or requests-per-minute thresholds per IP or per session
- Applies to **all bots**, even those with valid behavioral fingerprints
- Triggers before behavioral analysis runs in most implementations
- Thresholds are customer-configurable; Akamai does not publish defaults
- Effective against naive scrapers but easily defeated with request rate limiting and proxy rotation

### Behavior-Based (Bot Manager Premier Feature)
- Applies to specific high-value endpoints: login, checkout, add-to-cart, search
- Evaluates per-session behavioral profiles against ML models
- Not rate-dependent — a single request with wrong behavioral signals can score 100
- Accounts for advanced bots that deliberately slow down requests
- Requires sensor JavaScript execution to collect behavioral data
- **Key distinction**: rate-based blocking catches volume; behavior-based catches evasion

## 10. Known Bypass Techniques and 2026 Status

### Technique 1: TLS Impersonation with curl_cffi / Scrapy-Impersonate
**Status: Partially effective**
- Uses `curl_cffi` to impersonate Chrome/Firefox TLS fingerprint (JA3)
- Combined with proper HTTP/2 settings, bypasses network-layer detection
- Does NOT bypass JavaScript sensor challenges
- Works for: static page fetching, sites where sensor is not enforced on all endpoints
- Fails for: sites requiring sensor_data POST, behavioral challenge pages

### Technique 2: Sensor Data Generation (Static Reverse Engineering)
**Status: Unreliable / Short-lived**
- Reverse-engineering the obfuscated sensor script and reimplementing in Go/Python
- Repositories: `xvertile/akamai-bmp-generator`, `cirleamihai/akamai-1.7-cookie-generator`
- **Fatal flaw**: Akamai changes script hash regularly; v3 uses the script hash as an encryption key, so a static implementation breaks when Akamai rotates the script
- Canvas fingerprint cannot be realistically fabricated without a real browser GPU
- Success rate: ~30–60% depending on target and how recently script was updated

### Technique 3: Real Browser Automation with Stealth Patches
**Status: Moderate effectiveness**
- Playwright/Puppeteer with `playwright-stealth` or `puppeteer-extra-plugin-stealth`
- Patches `navigator.webdriver`, spoofs some fingerprint properties
- **Failures**: behavior detection (`❌ Behavior Detection` noted in niespodd/browser-fingerprinting research), Canvas fingerprint if GPU is flagged as headless-virtual, TCP OS mismatch if running in cloud
- Works best with: real (non-virtual) hardware, residential IP, proper mouse simulation (ghost-cursor)

### Technique 4: Residential/Mobile Proxy Rotation
**Status: Effective for IP-layer only**
- 4G/5G mobile proxies most effective (highest trust score from Akamai IP classification)
- Does not bypass JavaScript sensor or behavioral checks
- Required as a prerequisite for any bypass, not sufficient alone
- **2026 status**: Akamai's IP classification has improved significantly; ISP-labeled datacenter IPs are near-instantly flagged

### Technique 5: Cookie Harvesting from Real Browsers
**Status: Most reliable short-term**
- Extract valid `_abck` + `bm_sz` cookies from a real, non-automated browser session
- Replay these cookies in scraping requests
- **Limitation**: Cookies expire (bm_sz: ~4 hours, _abck: may persist longer but server-side validation can revoke)
- Session-bound validation may detect cookie use from a different IP/fingerprint than where it was generated

### Technique 6: Commercial Anti-Bot APIs
**Status: Highest success rate (~90–97%)**
- Services: ScrapFly, ScraperAPI, Hyper Solutions (hyper-sdk-js/go), Scrapeless
- These run real browsers or maintain up-to-date sensor generators at scale
- Hyper Solutions SDK handles: sensor generation, crypto challenge solving, sec_cpt challenge
- Cost: significant per-request pricing
- **2026 status**: Most reliable option; ScrapFly claims 97% success rate against Akamai

### Technique 7: JA3Proxy Chaining
**Status: Addresses one layer only**
- JA3Proxy: HTTPS proxy that re-establishes TLS using uTLS library with real browser cipher suites
- Chained with residential proxies covers IP + TLS layers
- Still requires JavaScript execution for sensor challenges
- Does not solve behavioral biometrics layer

## 12. Summary of Detection Layers (in Akamai's Order of Operation)

```
1. IP Classification (residential > mobile > datacenter/VPN/TOR)
2. TCP OS Fingerprint (p0f-style, compared to UA)
3. TLS Fingerprint (JA3 + JA4 hash comparison)
4. HTTP/2 Fingerprint (SETTINGS/WINDOW_UPDATE/PRIORITY/pseudo-header order)
5. Request Anomaly Detection (header order, version mismatches, malformed requests)
6. JavaScript Sensor Execution (if JS runs in browser):
   a. Device fingerprinting (canvas, WebGL, AudioContext, fonts, navigator)
   b. Behavioral event telemetry (mouse, keyboard, scroll, touch)
   c. Automation detection (webdriver flags, headless indicators)
7. Sensor Data Validation (POST to /akam/11/ endpoint):
   a. Cryptographic integrity check (PRNG-based encryption must be valid)
   b. Canvas fingerprint realism check
   c. Behavioral plausibility check
8. ML Risk Scoring (0–100, per-session cumulative)
9. Challenge dispatch if score in Strict tier (crypto challenge)
10. Interactive challenge if score in Aggressive tier
11. Session-level behavioral monitoring (ongoing, Premier only)
```
